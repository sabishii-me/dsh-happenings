# Happenings — DSH plugin

A sidebar entry called **Happenings**. The panel hosts the live event calendar from this repository: multi-day events render as range bars, clicking an event opens a new tab, and "N more" opens the day drawer.

The plugin serves the prebuilt site on the Host's origin and owns a small local API backed by SQLite. It does **not** need Wrangler, Workerd, a Cloudflare account, a site checkout or a D1 database.

## Install

The package lives in the `plugin/` subdirectory. Install it from the repository:

```sh
dsh plugin --profile <profile> add github:sabishii-me/dsh-happenings#path:/plugin
```

The plugin requires Node.js 22.5 or newer, because the bundled database uses `node:sqlite`.

The profile then lists it under `dependencies` and `dsh.profile.bundles`. Remove it with:

```sh
dsh plugin --profile <profile> remove dsh-happenings
```

## Architecture

```
DSH sidebar → Happenings panel → /dsh-happenings/app/   (same-origin static site)
                                → /dsh-happenings/api/*  (Host proxy to the local API)
```

- The API bundle is `plugin/lib/api.mjs`, generated from the Worker code in `src/worker`. It runs on Node and talks to SQLite through a small D1-compatible adapter.
- The database is seeded from `plugin/data/schema.sql` and `plugin/data/seed.sql` on first run. It defaults to `~/.dsh/happenings/happenings.db`.
- Static assets are snapshotted from `plugin/web` at registration time. No request path is used as a disk path, and symlinks are not followed.
- Only fixed endpoints are proxied: `health`, `events`, `meta`, `refresh`, `ics`, `export`.
- Refresh is the only `POST`; it is checked for same-origin. The proxy never forwards browser cookies, credentials or request bodies.

## Backend lifecycle

On load the plugin probes `/api/health`:

| Situation | Behaviour |
|---|---|
| Already healthy | Reused; nothing is started or killed |
| No service | `server.mjs` is spawned detached, logging to `~/.dsh/happenings/logs/happenings-backend.log`, waiting up to 30 s |
| Plugin unloaded | Only the process it started is killed |

With `backendUrl` pointing at a deployed site, or `autoStart: false`, the plugin never touches a local process.

```yaml
backendUrl: http://127.0.0.1:8790
requestTimeoutMs: 120000
# port: 8790
# dataDir: ~/.dsh/happenings
# dbPath: ~/.dsh/happenings/happenings.db
# autoStart: false
# adminToken: only for a deployment that requires it; used for refresh
```

`HAPPENINGS_BACKEND_URL`, `HAPPENINGS_PORT`, `HAPPENINGS_DATA_DIR` and `HAPPENINGS_DB` override the defaults.

## Development

To work on the plugin against a local checkout, link it instead of installing from git:

```sh
dsh plugin --profile <profile> add link:/absolute/path/to/dsh-happenings/plugin
```

From the repository root:

```sh
npm run build:plugin     # rebuild the API bundle, SQLite seed and plugin/web
npm run test:plugin      # host routes, client registration, lifecycle
node plugin/server.mjs   # run the bundled local API directly
```

`plugin/web`, `plugin/lib/api.mjs` and `plugin/data/*.sql` are generated by `npm run build:plugin`. Commit them so an install from git ships the current UI and API.

## Tests

`npm run test:plugin` covers route registration, proxy and security behaviour, and the reuse/start/stop lifecycle. The site has its own unit and Playwright suites (`npm test`, `npm run e2e`).
